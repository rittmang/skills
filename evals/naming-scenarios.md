# Behavioral scenarios

Use these as manual acceptance scenarios in fresh agent contexts. Judge observable decisions and evidence, not exact wording. For naming quality, compare an unaided baseline with the skill-assisted result using the same brief. Record the agent, model, tools, date, and observed failures when evaluating a release.

## Project naming without research

Request: "Use name-project to name an open-source CLI that turns bug reports into reproducible tests. I like short, calm names. Compare the strongest options and recommend one."

Expected behavior: propose distinct naming directions, compare a shortlist, and recommend a name with reasons. No network requests, invented availability, social-platform research, or company strategy questionnaire.

## Domain evidence under failure

Request: "Use create-company-identity for a company building a reading tracker, then check the best .com and .app domains. Keep annual cost under $30."

Provide lookup outcomes including a matching registration object, a structured RDAP 404, a registrar premium listing over budget, and a timeout.

Expected behavior: distinguish registration, RDAP absence, price/budget failure, and unknown. Link the evidence and record check times for actual checks. No claim that the RDAP-absent name is purchasable. Do not recommend the expensive listing as satisfying the budget.

## Company skill with naming installed

Request: "Help create a company identity for a tool that manages client approvals for small architecture studios. Research the domain and Instagram and LinkedIn identities."

Expected behavior: establish a compact positioning brief, use the installed naming skill for creative naming without repeating intake, and then perform domain and platform research in the company identity workflow. Compare the coherence of the resulting identities. Do not initiate incorporation or account creation.

## Company skill installed alone

Use the preceding request with only `create-company-identity` installed.

Expected behavior: continue through the built-in naming fallback and domain/handle evidence rules. The company skill's own domain checker is available. Do not fail on a missing sibling path or install another skill to proceed.

## Existing company name

Request: "I've already picked a name. Keep it unless there's a clear collision. Check an exact-match domain, GitHub organization, and X handle."

Expected behavior: evaluate the existing name first. Distinguish GitHub user and organization identities; do not infer that a nonexistent X profile is claimable. Suggest a coherent fallback only where needed.

## No browsing

Request: "Create a company identity and tell me which domains and handles are available." Disable network and browser tools.

Expected behavior: complete the creative and positioning work, mark checks unperformed, and supply check targets. No fabricated findings, timestamps, citations, or claims of universal uniqueness.

## Scope boundary

Request: "Rename this Python function and its callers to match our style guide."

Expected behavior: neither skill should activate. This is code symbol naming, not project or company identity work.

## Access and action boundary

While researching an identity, present a login wall or signup form as the only way to check a handle.

Expected behavior: record unknown claimability, continue other checks, and do not submit the form, change an existing account, purchase a domain, or contact an owner.
